AI 写错代码，常常不是因为语法。它以为自己理解了需求，于是把一个局部改动做成了另一套流程。

我后来把这个问题从“怎么把提示词写得更长”换成另一个问题：**这次改动如果理解偏了，返工和风险有多大？** 偏小，就用 Skill 和测试把它做完。偏大，才为它建立一份 OpenSpec。

## OpenSpec 是什么

OpenSpec 是 AI 编程里的一种规格驱动工作流。它用一组约定，让人或 Agent 在写代码之前先写清：为什么改、改哪些行为、不改哪些行为、怎样算做完。

它容易和几样现成的东西混在一起，但这几样都替代不了它：

- 它不是 OpenAPI。OpenAPI 描述接口契约，不描述一次产品变更为什么发生、影响哪些页面。
- 它不是模型，也不是正在运行的 Agent。它不生成回答，也不替你执行任务。
- 它也不是又一份 README。README 告诉后来的人项目怎么跑；OpenSpec 强调的是**一次变更的生命周期，以及这条变更能不能被验证**。

我用它记住的最小结构是这样：

```text
openspec/
├── specs/                 # 已经生效的长期行为
└── changes/               # 每一次功能迭代的记录
    └── [change-name]/
        ├── proposal.md    # 为什么改、范围是什么
        ├── design.md      # 技术设计
        ├── tasks.md       # 实施任务
        └── specs/         # 这次变更要满足的行为
```

四个项目里的文件名并不完全一样。有的把行为要求写成 `spec.md`，有的在变更里再放 `verification.md`，有的把做完的变更收进 `changes/implemented/`。共同的部分是这条线：

**提案、设计、实现、验证、归档。**

提案回答为什么改、改到哪里为止。设计回答数据和模块怎么接。实现按任务推进。验证把成功、失败和边界场景留成证据。归档则把仍然有效的规则收进 `specs/`，让下一次改动先读现行规则，而不是从聊天记录里翻。

## 先看影响面，再决定用多重的流程

标准管理后台里的普通增删改查，通常不需要这套目录。一个页面、一份接口、一组表单校验，用 Skill 加一份很短的需求说明就够了。

需要 OpenSpec 的，是**需求复杂、影响面大、AI 容易把规则理解偏**的改动。我按这个标准把日常需求分成三档：

| 需求类型 | 推荐方式 |
| --- | --- |
| 修改文案、表格列、筛选项、简单样式 | 直接使用 Skill |
| 新增标准 CRUD 页面，涉及接口、表单校验、权限、分页 | Skill、简短设计文档和测试 |
| 跨页面流程、复杂状态、批量操作、上传、导入导出、权限联动 | 使用 OpenSpec |
| 影响公共组件、路由、数据模型或多个业务模块 | 使用 OpenSpec |
| 高风险功能，例如发布、下架、支付、数据删除、批量变更 | 使用 OpenSpec |

对应到执行，也不是“整个仓库切换到 OpenSpec”，而是一条分层路径：

```text
简单改动
  -> Skill
  -> lint / typecheck

普通 CRUD 页面
  -> 页面契约
  -> 简短 design.md
  -> 单元测试
  -> lint / typecheck / build

复杂业务变更
  -> OpenSpec
  -> design / tasks / acceptance
  -> Agent 实现
  -> 自动验证
  -> 归档
```

下面四个项目，就是按这条路径取舍的。

## 管理后台：大多数改动停在 Skill

`micro-sub-app` 是一个管理后台。列表、筛选、编辑和 Vue 2 到 Vue 3 的机械迁移，我直接交给 Skill。这些改动的行为边界清楚，偏了也容易从页面上看出来。

下面这些会多留一份轻量设计，但仍然不单开一套 OpenSpec：

- 新增一个完整管理模块；
- 接入一组新的后端接口；
- 上传、导入、导出；
- 需要补比较多测试的改动。

设计文档在这里只回答页面、接口和测试范围，不追求把每次点击都写成长期规范。

真正适合 OpenSpec 的，是这几类：

1. 一个功能同时碰到多个页面和公共组件。
2. 状态规则本身就复杂，不能靠界面文案推断。
3. 权限、菜单、接口和页面行为必须保持一致。
4. Agent 要连续做多步，中间不能丢上下文。
5. 需求还会变，需要能对上“需求、代码、测试”。
6. 多个 Agent 或多个人并行改同一块业务。
7. 上线风险高，必须能审计，也必须能回滚。

所以这个项目更实用的做法是分层，而不是把每个列表页都写成规格。

## 运营站：只给跨页面的新功能建规格

`app-operation-web` 的页面不算多，业务却不容易被一句需求说完。交易回收要经过设备登记、资格验证、地址、取件、物流和协议。老带新活动同时有推荐官和购买者两条流程。页面背后还有多组后端 API、微信能力、原生 App 调用和埋点，失败场景和状态也不少。

这个仓库没有为了 OpenSpec 做一次全量迁移。交易回收、老带新这类新功能或大改动，使用轻量 OpenSpec。小的界面调整和局部缺陷，仍按普通任务处理。跨页面、跨接口、跨端能力的需求出现时，再补一份规格。

比如“用户可以修改取件地址”，规格里至少要写清规则和验收，而不是只写一句功能名：

- 只有订单处于待取件状态时允许修改。
- 修改成功后刷新订单详情。
- 修改失败时保留原地址。
- 提交期间禁止重复提交。
- App 内和 H5 的入口行为不同。

验收要覆盖成功、失败、重复点击，以及订单状态在提交过程中发生变化。Agent 后面写的代码和测试，都要能回到这些句子。

仓库里的落地比一份概念图更具体：

- `openspec/README.md` 写使用规则、目录约定，以及改逻辑前先读哪些文件。
- `openspec/specs/trade-in-lifecycle/spec.md` 记录以旧换新的状态、流程边界、接口适配和关键不变量。
- `openspec/specs/referral-campaign/spec.md` 记录推荐官与购买者流程、优惠码状态、鉴权恢复和刷新规则。
- `openspec/specs/platform-boundaries/spec.md` 记录 NativeBridge、微信、小程序、分享 URL、环境分流和埋点边界。
- `openspec/changes/README.md` 说明怎样新建一次 change，并给出模板。
- `openspec/changes/implemented/` 保留已经落地、以后还要回看的变更，包括交易回收状态流、交易回收分享与唤起 App、老带新活动、微信小程序兑换。

![app-operation-web 的 OpenSpec 目录：changes/implemented 中展开老带新活动的 proposal、tasks 和 verification，同级还有微信兑换、交易回收状态流、分享与唤起 App；specs 中有平台边界、老带新和以旧换新三份规范](/images/posts/openspec-practice/app-operation-web-tree.png)

这套文档目前是轻量写法，还没有接入官方 OpenSpec CLI 做校验。目录和阅读顺序先把上下文固定下来。根目录的 `AGENTS.md` 要求：改逻辑前先读入口、相关 spec 和历史 change，再读源码和测试。会读取 `AGENTS.md` 的 Agent 能沿着这条顺序工作；其他工具则要自己支持这份约定。

之后的人，包括下一次进来的 Agent，阅读顺序是固定的：

1. `openspec/README.md`
2. 和这次改动相关的 `specs/*.md`
3. `openspec/changes/` 里相近的历史 change
4. 对应的源码和测试

新需求写到 `openspec/changes/` 下的新目录，先在 `proposal.md` 里写行为和验收，再改代码。完成后补 `tasks.md` 和验证结果。

实际让 Agent 开工时，我不会只说“改一下老带新”。更有用的说法是：先按 `AGENTS.md` 阅读相关规范，列出受影响的规则；行为要变，就先补 change，再改代码和测试。

## 这个博客：规格管变更，计划文档继续留着

栈间笔记看起来只是一个内容站，变更却经常跨过内容模型。它同时有 Next.js 的页面、路由和交互，公开文章和本机私密笔记，VuePress 迁移，以及搜索、RSS、Sitemap、封面、发布、隐私和版权约束。这些规则如果只写在一次对话里，下次迁移或改搜索时很容易被覆盖掉。

这里采用的是仓库内的轻量 OpenSpec，不增加生产依赖，也不把 `docs/plans` 替换掉。长期设计仍放在 `docs/plans`。一次具体变更放在 `openspec/changes/` 的独立目录里，里面是 `proposal.md`、`spec.md`、`design.md` 和 `tasks.md`。已经生效的规则放在 `openspec/specs/`，目前包括内容发布与可见性、VuePress 迁移、站点索引与生成。知识库和迁移那次变更，则作为可以回看的 change 留在 `openspec/changes/knowledge-base-and-migration/`。

校验由 `scripts/validate-openspec.ts` 完成，命令是：

```bash
npm run openspec:check
```

它检查变更目录的命名、必需文件和标题、任务是否仍未勾选，以及规格里有没有常见凭据写法。脚本只读 Markdown，不改文件，也不访问网络。

单篇文章的润色、错别字和非常明确的一行样式，可以不走完整变更。一旦改的是路由、搜索、迁移、发布或隐私边界，就先写 change。设计取舍记在 `docs/plans/2026-10-30-openspec-workflow-design.md`：比较过官方 CLI、只扩展旧计划文档，以及现在这套 Git 里的 Markdown 规格，最后选了能审查、也不改构建链的一种。

## 制谱工具：协议和数据边界才进入规格

LiberScore 同时有 React 界面、Node 服务、LiberLive 协议适配、IndexedDB、登录和设备连接，还有 AI 制谱。一次需求经常要同时说明范围、协议依据和验收标准，所以它适合 OpenSpec。错别字和纯格式调整则跳过。

项目里同样使用轻量目录和校验脚本，不为此增加生产依赖。需要建规格的范围是：

- 页面行为和异步流程；
- App 接口、协议和设备命令；
- 数据模型、草稿和 IndexedDB；
- 登录、权限和账号隔离；
- AI 制谱、播放、MIDI、蓝牙这类跨模块功能。

一次需求一个目录，例如 `openspec/changes/2026-10-31-save-to-app-retry/`。里面四份文件各管一件事：`proposal.md` 写为什么改、改什么、不改什么；`design.md` 写技术方案、数据边界和错误处理；`spec.md` 写具体要求、成功和失败场景、验收条件；`tasks.md` 写实现和验证任务。`openspec/templates/` 提供这四份模板。已经实现并确认过的长期行为，收进 `openspec/specs/`。

`npm run openspec:check` 在这里检查的是结构，不是业务对错：变更目录怎么命名，必需文件和标题在不在，有没有场景，有没有验收条件，任务里有没有复选框。结构齐全，Agent 才不容易把“保存失败后重试”写成一次无条件覆盖。

## 下一次可以先问三个问题

我现在不会先问“这个项目用不用 OpenSpec”。我会先问这次改动：

1. 行为能不能用几句话写完，并指出不改什么？
2. 它会不会同时碰到多个页面、公共组件、接口、权限或端能力？
3. 做错了，能不能靠一次页面查看发现，还是必须留下可回放的规则和测试？

三个答案都轻，就用 Skill，跑 lint 和类型检查。只是一张标准页面，就补一页短设计和测试。只要状态、权限或跨端行为开始分叉，就把提案和验收先写下来，再让 Agent 实现。

OpenSpec 的价值不在目录本身。它让下一次修改的人和 Agent，都能从现行规则出发，而不是从一份看起来完整的代码出发。
