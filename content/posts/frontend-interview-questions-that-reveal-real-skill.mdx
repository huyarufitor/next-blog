筛选中高级前端简历时，我经常看到这些词：精通 Vue、熟悉 React、主导性能优化、负责微前端改造、搭建 Monorepo、从 0 到 1、带领团队、落地 AI Coding。

这些词都可能是真的，但它们本身几乎没有区分度。

同样写着“Vue 2 升级 Vue 3”，有人只是跟着任务改生命周期，有人设计了兼容层、迁移顺序、灰度策略和回滚机制。都写“性能提升 50%”，有人只能复述结果，有人能讲清指标口径、采样环境、瓶颈定位和收益归因。

我重新翻看了几份有代表性的中高级前端简历，发现真正值得面试的，不是候选人列了多少技术，而是他能否把一个项目讲成完整的因果链：为什么做、他做了什么、为什么这样做、出过什么问题，以及结果如何被证明。

这篇文章整理了一套我认为更接近真实招聘场景的题目。它不提供唯一标准答案，而是帮助面试官识别候选人的参与深度、工程判断和表达可信度。

> 文中所有项目线索均已做匿名化和抽象处理。它们只是设计面试题的能力信号，不代表对任何候选人经历真实性的判断。

## 先别急着问八股，先建立五层追问

面对简历上的任何亮点，我通常沿着五层继续问：

1. **事实层**：你具体负责哪一部分，边界在哪里？
2. **原理层**：这个方案为什么能解决问题？
3. **取舍层**：还比较过什么方案，为什么没选？
4. **故障层**：遇到过什么失败，如何发现、止损和复盘？
5. **结果层**：收益如何测量，能否排除其他因素？

一个真正做过项目的人不一定表达得特别华丽，但通常能给出时间、上下游、限制条件、关键决策和失败细节。只背过概念的人，往往会在第二层之后开始重复名词。

下面的 30 道题分为三个层级。面试中不需要全部问完，可以根据岗位和简历挑选。

## 第一层：基础能力，验证候选人的基本盘

这一层适合所有 4 年以上的前端候选人。重点不是背诵定义，而是判断他能否把基础知识用于排查真实问题。

### 1. 一次用户点击，到页面更新，中间发生了什么？

**主问题**：从浏览器接收到点击事件开始，到 Vue 或 React 完成页面更新，请描述完整过程。

**建议追问**：事件循环、微任务、框架调度和浏览器渲染分别在什么阶段？连续多次状态修改为什么可能只渲染一次？

**优秀回答信号**：能把事件处理、状态更新、批处理、虚拟 DOM 或响应式依赖、样式计算、布局和绘制串成一条链，并说明框架版本差异。

**风险信号**：只会背宏任务和微任务顺序，无法解释它们与一次真实渲染的关系。

### 2. 如何判断页面卡顿发生在 JavaScript、布局还是绘制？

**主问题**：用户反馈“页面操作很卡”，你会如何用浏览器工具定位？

**建议追问**：Long Task、Layout、Paint、内存曲线和帧率分别能说明什么？如何构造可重复的测试场景？

**优秀回答信号**：先定义复现条件，再使用 Performance、Network、Memory 等工具建立证据，能区分主线程阻塞、强制同步布局和资源问题。

**风险信号**：一上来就提出防抖、节流或虚拟列表，没有先确认瓶颈。

### 3. TypeScript 在大型项目里真正解决了什么问题？

**主问题**：除了“减少类型错误”，TypeScript 给团队协作带来了什么？

**建议追问**：接口返回值、表单 Schema、组件 Props 和跨包 API 应如何建模？何时使用泛型、判别联合、`unknown`，何时不该使用复杂类型？

**优秀回答信号**：能讨论类型边界、领域模型、重构成本和编译性能，也承认类型系统不能替代运行时校验。

**风险信号**：把 `any` 全部换成接口就算完成类型治理，或者追求难以维护的类型体操。

### 4. Vue 3 的响应式为什么不能简单理解为“把 defineProperty 换成 Proxy”？

**主问题**：请从依赖收集和触发更新的角度解释 Vue 3 响应式。

**建议追问**：`ref` 与 `reactive` 如何选择？解构为什么可能丢失响应性？数组、Map、computed 和 watch 的行为有什么差异？

**优秀回答信号**：能从代理、effect、track、trigger 和调度解释行为，并能联系实际 bug。

**风险信号**：只会说 Proxy 可以监听新增属性，无法解释依赖关系和更新时机。

### 5. React Hook 最常见的闭包问题是怎么产生的？

**主问题**：为什么定时器、事件监听或异步请求里经常读到旧状态？

**建议追问**：依赖数组、函数式更新、`useRef`、取消订阅分别适合什么场景？如何避免为了“消除警告”盲目补依赖？

**优秀回答信号**：能解释每次渲染形成独立闭包，知道副作用的创建与清理边界，并考虑并发渲染下的正确性。

**风险信号**：把所有值放进 `useRef`，或通过关闭 lint 规则解决问题。

### 6. 前端状态应该放在哪里？

**主问题**：组件状态、全局状态、URL 状态和服务端状态应该如何划分？

**建议追问**：列表筛选条件、登录用户、接口缓存和跨页面草稿分别放哪里？为什么？

**优秀回答信号**：根据状态生命周期、共享范围、可恢复性和数据所有权判断，而不是根据项目用了 Pinia、Redux 或 Zustand 判断。

**风险信号**：习惯把所有状态放进全局 Store，导致重复数据和同步困难。

### 7. 一个可靠的请求封装应该处理哪些问题？

**主问题**：如果让你设计项目的请求层，你会把哪些能力放进去？

**建议追问**：超时、取消、重试、并发去重、刷新令牌、错误归一化和幂等性如何处理？哪些逻辑不应该放在拦截器？

**优秀回答信号**：能区分传输层、认证层和业务层，知道重试可能放大流量，也能解释刷新令牌的并发控制。

**风险信号**：用一个全局拦截器处理所有错误，业务只能根据字符串判断异常。

### 8. 为什么“用了懒加载”不等于性能已经优化？

**主问题**：路由懒加载、组件懒加载和图片懒加载分别解决什么问题？

**建议追问**：拆包过细会有什么副作用？预加载时机如何选择？如何防止首屏请求瀑布？

**优秀回答信号**：能讨论包体、请求数量、缓存命中、关键资源优先级和交互时延之间的平衡。

**风险信号**：只要看到大组件就使用异步组件，不测量首屏和交互指标。

## 第二层：项目深度，验证简历是不是“亲自做过”

这一层从简历高频关键词出发。题目本身不难，难的是候选人能否讲清工程约束和决策过程。

### 9. 如果要把一个大型 Vue 2 项目迁移到 Vue 3，你怎么拆阶段？

**主问题**：项目页面很多、业务持续迭代、不能停机重写，你会如何制定迁移路线？

**建议追问**：依赖盘点、兼容构建、公共组件、状态管理、路由、自动化转换、灰度和回滚分别怎么安排？

**优秀回答信号**：先建立依赖与风险清单，以可独立验证的业务切片迁移，同时设计双轨运行、质量门禁和回滚条件。

**风险信号**：回答集中在生命周期名称变化，没有版本治理和业务连续性方案。

### 10. 简历写“LCP 从几秒降到一秒多”，你如何证明是自己的方案带来的？

**主问题**：请说明优化前后的测量口径和归因方法。

**建议追问**：实验室数据与真实用户数据有什么区别？设备、网络、缓存、样本量和版本变化如何控制？

**优秀回答信号**：能说明基线、分位数、采样窗口、对照版本和监控平台，并把收益拆到资源、渲染或接口环节。

**风险信号**：只展示一次 Lighthouse 分数，没有真实用户数据或稳定测试环境。

### 11. 万级列表做到 60fps，需要解决哪些问题？

**主问题**：虚拟列表除了“只渲染可视区域”，还要处理什么？

**建议追问**：动态高度、快速滚动、锚点保持、图片加载、滚动恢复和无障碍如何处理？

**优秀回答信号**：能讲清可视区计算、缓冲区、位置估算与修正，以及测量和交互细节。

**风险信号**：只会引用一个虚拟列表库，不知道动态高度为什么会跳动。

### 12. 微前端解决了什么组织问题，又制造了什么技术问题？

**主问题**：什么情况下你会选择微前端，什么情况下不会？

**建议追问**：样式隔离、依赖重复、路由、鉴权、通信、独立发布和故障隔离如何设计？

**优秀回答信号**：先谈团队和发布边界，再谈框架；能说明主应用与子应用契约、版本兼容和观测能力。

**风险信号**：因为系统多就使用微前端，或把框架名当作架构方案。

### 13. Monorepo 变大以后，构建为什么会越来越慢？

**主问题**：请设计一个包含多个应用和共享包的 Monorepo 构建流程。

**建议追问**：任务依赖图、增量构建、远程缓存、版本发布、幽灵依赖和权限边界怎么处理？

**优秀回答信号**：能解释任务输入输出和缓存键，知道包管理、任务调度与发布工具解决的是不同问题。

**风险信号**：认为把代码放进 pnpm workspace 就完成了 Monorepo 治理。

### 14. Webpack 升级或更换 Vite 时，最容易低估什么？

**主问题**：如果一个旧项目要升级构建工具，你会先收集哪些信息？

**建议追问**：插件兼容、动态导入、环境变量、代理、CSS、浏览器目标和产物差异如何验证？

**优秀回答信号**：先建立构建行为基线和产物对比，分离工具升级与业务改造，并保留可回退路径。

**风险信号**：只比较开发服务器启动速度，不检查生产产物和运行兼容性。

### 15. iframe 加 postMessage 做单点登录，安全边界在哪里？

**主问题**：这种方案有哪些攻击面和浏览器限制？

**建议追问**：origin 校验、消息格式、令牌存储、第三方 Cookie、登出同步、重放攻击和 CSP 如何处理？

**优秀回答信号**：能明确可信源、最小消息协议和令牌生命周期，也知道浏览器隐私策略可能让旧方案失效。

**风险信号**：使用 `*` 作为目标源，或认为把 token 放进 localStorage 就完成了 SSO。

### 16. Electron 的 contextIsolation 到底隔离了什么？

**主问题**：网页如何安全调用桌面能力？

**建议追问**：preload、contextBridge、IPC、权限白名单和参数校验如何设计？降低 Electron 版本兼容旧系统时有哪些风险？

**优秀回答信号**：坚持最小能力暴露，能讨论主进程、渲染进程边界和版本回退带来的安全及依赖问题。

**风险信号**：为了方便直接启用 Node integration，或把整个 IPC 对象暴露给页面。

### 17. 跨端方案如何避免“一套代码，多端一起坏”？

**主问题**：使用 UniApp、Taro 或小程序原生开发多个端时，公共层应该抽象到哪里？

**建议追问**：平台能力差异、登录支付、组件样式、包体限制、灰度和端上监控怎么处理？

**优秀回答信号**：抽象稳定的领域逻辑和协议，把平台差异留在适配层，并保留真机测试矩阵。

**风险信号**：以代码复用率作为唯一目标，为了复用制造大量条件分支。

### 18. WebSocket 断线重连为什么不能只写一个 setTimeout？

**主问题**：请设计一个面向弱网环境的实时连接客户端。

**建议追问**：心跳、指数退避、抖动、网络切换、消息补偿、顺序、重复消费和服务端过载如何处理？

**优秀回答信号**：能同时考虑客户端状态机、服务端压力和消息语义，知道重连成功不等于数据已经一致。

**风险信号**：固定间隔无限重连，断线后不补数据，也没有可观测状态。

### 19. SSE、WebSocket 和轮询应该怎么选？

**主问题**：AI 流式输出、设备监控和任务进度三个场景分别如何选择？

**建议追问**：单向或双向、连接数、代理超时、断点续传、鉴权和浏览器兼容如何影响选择？

**优秀回答信号**：从通信方向、数据频率、基础设施和恢复语义做选择，而不是追求更新的技术。

**风险信号**：认为实时业务一律使用 WebSocket，或者不知道 SSE 的重连与事件 ID。

### 20. 前端监控 SDK 如何避免自己成为性能和流量问题？

**主问题**：错误捕获、去重、采样和上报应该如何设计？

**建议追问**：资源错误、Promise、请求错误和框架错误分别怎么捕获？指纹、批量、离线缓存、Source Map 和隐私脱敏怎么做？

**优秀回答信号**：能设计稳定指纹、采样策略和发送队列，并明确 SDK 自身异常不能影响宿主应用。

**风险信号**：只会注册几个全局监听器，所有错误原样实时上报。

### 21. 低代码表单或页面编辑器，Schema 应该怎么设计？

**主问题**：如何让配置协议既能扩展，又不把业务逻辑全部变成字符串？

**建议追问**：组件注册、属性约束、联动表达式、版本迁移、撤销重做和安全执行如何实现？

**优秀回答信号**：能区分领域 Schema、渲染器和编辑器状态，考虑版本化、校验、沙箱和可测试性。

**风险信号**：把任意 JavaScript 存进配置并直接执行，或没有 Schema 版本策略。

### 22. Node BFF 的边界在哪里？

**主问题**：前端团队什么时候需要 BFF，什么时候应该让后端服务直接提供接口？

**建议追问**：聚合、缓存、鉴权、协议转换、超时、熔断和日志怎么做？BFF 如何避免变成新的单体后端？

**优秀回答信号**：能用客户端体验和团队边界解释价值，也能说明容量、降级和责任归属。

**风险信号**：把所有业务逻辑搬进 Node，只因为前端更熟悉 JavaScript。

## 第三层：高级前端与负责人，验证工程判断

负责人岗位不只需要“做得出来”，还要能在信息不完整、多人协作和线上风险中做选择。

### 23. 接手一个没有测试、发布缓慢的历史项目，你先改什么？

**主问题**：请给出前 30 天的治理顺序。

**建议追问**：现状数据怎么收集？lint、类型检查、单测、构建验证和发布审批谁先谁后？

**优秀回答信号**：先建立可见性和最小质量基线，从高频变更与高风险链路开始，不用一次性重构阻塞业务。

**风险信号**：第一步就是升级所有依赖、重写框架或追求覆盖率数字。

### 24. 你如何验证简历上的量化成果？

**主问题**：候选人说“效率提升 50%”“客诉下降一半”，你会如何继续问？

**建议追问**：基线是什么、统计周期多长、样本来自哪里、还有哪些同时发生的变化、候选人个人贡献是什么？

**优秀回答信号**：候选人能说明指标定义、数据来源、前后对照和自己的责任边界，允许结果存在误差。

**风险信号**：只有整齐的百分比，没有原始口径；把团队、后端或业务变化全部归因给个人技术方案。

### 25. 一个高风险核心链路上线前，你如何设计灰度和回滚？

**主问题**：以登录、支付或远程更新为例，给出发布方案。

**建议追问**：灰度单位、关键指标、自动止损阈值、数据兼容、双写和回滚演练怎么处理？

**优秀回答信号**：从功能开关、版本兼容、监控告警到操作手册形成闭环，并提前验证回滚不是纸面方案。

**风险信号**：把“发版失败就回滚代码”当作完整答案，忽略数据和客户端版本。

### 26. 技术选型意见不一致时，你如何推动决策？

**主问题**：团队在微前端、状态管理或构建工具上争论不休，你会怎么办？

**建议追问**：如何确定决策人、评价指标、验证范围和截止时间？PoC 应该验证什么？

**优秀回答信号**：把偏好转成约束与指标，用小范围实验消除关键不确定性，并记录决策和退出条件。

**风险信号**：依赖职位拍板，或为了所有人满意而长期不做决定。

### 27. Code Review 如何既保证质量，又不拖慢交付？

**主问题**：你会如何制定团队 Review 规则？

**建议追问**：什么由自动化检查，什么必须人工判断？大 PR、紧急修复和争议如何处理？

**优秀回答信号**：自动化风格与基础错误，人工关注设计、风险和可维护性；鼓励小批次提交并明确响应时限。

**风险信号**：Review 只挑格式和命名，或负责人必须审批所有代码形成瓶颈。

### 28. 请讲一次你主导处理的线上事故

**主问题**：从发现、止损、定位、修复到复盘，按时间顺序讲。

**建议追问**：当时缺少什么信息？做过哪些错误判断？怎样防止同类问题再次发生？

**优秀回答信号**：能说出不完美的决策和协作过程，区分直接原因与系统原因，并有后续行动项。

**风险信号**：工作多年从未遇到事故，或者事故永远是别人造成的。

### 29. AI Coding 进入团队后，质量责任如何划分？

**主问题**：如何在真实业务中使用 AI 提效，而不是只生成 Demo？

**建议追问**：上下文如何提供？敏感代码、依赖许可、错误答案、测试、Review 和效果评估怎么处理？

**优秀回答信号**：把 AI 放进有边界的工作流，用规则、知识库、测试和人工审查控制风险，衡量交付周期与返工率。

**风险信号**：只统计生成代码量，或者把模型输出直接合并到生产分支。

### 30. 如果只能用一个项目证明你适合这个岗位，你会选哪个？

**主问题**：请用五分钟说明背景、约束、个人决策、失败、结果和复盘。

**建议追问**：如果重来一次会改什么？项目中哪项成果即使没有你也会发生？

**优秀回答信号**：候选人能主动划清个人与团队贡献，讲清关键决策，并对结果保持克制。

**风险信号**：继续罗列技术栈，无法说明最重要的判断，也不承认任何遗憾。

## 一套可以直接使用的 60 分钟流程

题目不是越多越好。一次中高级前端面试，我会这样分配：

### 前 5 分钟：校准经历

让候选人选择一个最能代表自己的项目，用“背景、角色、难点、结果”快速介绍。面试官同步确认他真正负责的边界。

### 5 至 20 分钟：基础能力

从第一层选 3 道题，其中至少一道结合候选人的主技术栈，一道结合浏览器或性能，一道结合 TypeScript 或状态管理。

### 20 至 45 分钟：项目深挖

从简历关键词中选择 2 个主题，每个主题沿五层追问到底。候选人写了 Monorepo，就不要同时浅问微前端、Electron 和 Node；问深一个真实项目，比扫过十个名词更有价值。

### 45 至 55 分钟：负责人能力

高级岗位从第三层选择 2 道题，重点观察候选人如何处理不确定性、风险和团队协作。中级岗位可以改成一个小型方案设计题。

### 最后 5 分钟：候选人提问

候选人问什么也能反映关注点。优秀候选人通常会关心业务目标、团队协作方式、技术债、岗位成功标准和决策空间。

## 五维评分表

每个维度建议按 1 至 5 分独立记录，并为分数写下一条事实证据。

| 维度     | 重点观察                 | 高分表现                               |
| -------- | ------------------------ | -------------------------------------- |
| 基础能力 | 浏览器、语言、框架和调试 | 能用原理解释现象，也能落到排查工具     |
| 项目深度 | 责任边界、难点和失败     | 细节具体，因果完整，能说明自己的贡献   |
| 工程判断 | 选型、迁移、质量和风险   | 能比较方案，理解成本，并设计退出路径   |
| 业务意识 | 指标、用户和交付价值     | 技术动作与业务结果有关联，数据口径清楚 |
| 协作表达 | 沟通、Review 和复盘      | 表达有结构，尊重事实，能承认不确定性   |

不要在面试结束后凭“感觉不错”统一打分。先记录证据，再独立评分，最后讨论分歧。否则表达流畅、背景相似或技术偏好一致，很容易被误判成能力强。

## 面试官最容易犯的四个错误

### 把冷门知识当作区分度

候选人没记住某个 API，不代表不会解决问题。真正有效的问题应该允许他澄清、假设、推导和验证。

### 只问自己擅长的技术

面试不是找一个和自己知识结构完全相同的人。题目应该从岗位成功标准和候选人经历出发，而不是用个人知识盲区制造优越感。

### 听到名词就默认做过

简历里出现 React、微前端或 AI，不代表候选人负责过关键决策。继续问责任边界、替代方案、故障和指标，事实会自然浮现。

### 用标准答案压制不同方案

工程问题经常没有唯一答案。比“选了什么”更重要的是候选人掌握了哪些约束、承担什么成本，以及如何发现选择错了。

## 最后

一场好的技术面试，不应该是面试官证明自己知道得更多，也不应该是候选人表演背过多少题。

它应该是一次有时间限制的共同问题分析：面试官提供真实约束，候选人展示如何建立事实、拆解问题、做出取舍并验证结果。

简历上的技术关键词只是入口。真正的水平，藏在关键词后面的决策、失败和证据里。
