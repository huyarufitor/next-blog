苏联解体后，地图上发生了什么变化？

德国统一之前，欧洲地图是什么样子？

课本里的“非洲独立年”，放到地图上，又会呈现怎样的变化？

这些名字和年份，我们可能都听过。但只读一段文字，往往很难把事件、位置和边界连在一起。

如果世界地图也有一条进度条，可以往回拖动，可以停在某个年份，还能切换事件前后的画面呢？

这就是 **「经纬之间 · 世界历史地图」** 想提供的体验：把时间轴放到地图旁边，让你一边读历史，一边寻找它发生的位置。

**[打开地图，先从 1991 年开始探索 →](https://huyarufitor.github.io/history-atlas/)**

## 先试这一幕：从苏联解体前，切换到解体后

打开网站，你会看到世界地图、年份时间轴，以及对应的历史专题。

选中“苏联解体”，点击“在地图上聚焦”，再分别切换“变化前”和“变化后”。这个专题比较的是 **1991 年初与年末** 的地图快照。

同一片地理空间，换了时间，就有了不同的政治版图。原本抽象的“解体”，开始有了可以观察的空间关系。

但这组对比也留了一个重要提醒：它呈现的是一个阶段的变化，并不意味着所有加盟共和国在同一天突然独立。

你可以先看变化，再读解释，最后沿着资料链接继续查阅。地图负责帮你找到问题，文字和来源帮助你理解问题。

## 给地图加上时间，会多出哪些玩法？

### 拖动年份，换一个时代看世界

时间轴支持选择年份、输入年份和逐年播放，也可以选择具体日期，检索数据源在该日期对应的边界记录。

停在一个年份观察，再切到另一个年份比较，比连续看过所有年份更容易发现细节。键盘左右方向键可以切换年份，空格可以播放或暂停。

**时间轴可选择 1900—2026 年，不过当前国界数据只覆盖至 2019 年末。** 选择 2020—2026 年时，网站会提示“边界数据待补充”，不会把旧地图当成新年份的地图展示。

### 从一个事件出发，而不是面对整张地图发呆

不知道从哪里开始，可以先打开历史专题。

目前项目整理了 **17 个专题**，包括奥匈帝国瓦解、印巴分治、非洲独立年、德国重新统一、苏联解体、捷克斯洛伐克和平分离和南苏丹独立等。

每个专题都有事件说明、前后快照日期、区域聚焦和外部参考资料。读到一个感兴趣的事件，点一下就能把视线移到相关地区。

这里有一个很值得留意的现象：**历史事件发生了，地图轮廓未必立即改变。** 政体变化、独立宣告、条约签署和边界生效，可能发生在不同日期。比如德意志帝国终结专题就提醒读者，帝制结束与后续领土调整不能混为一谈。

### 搜索一个地区，沿着它的问题继续看

网站支持搜索当前日期地图中的国家或地区，也可以切换欧洲、亚洲、非洲等区域视角，拖动和缩放地图。

搜索依据的是当前日期的数据，所以不能默认今天存在的国家，在任何历史年份都能以同样的名称找到。

除了地图本身，项目还提供地区历次边界记录、几何版本、来源行号和核查台账。想进一步追问“这块边界依据什么画出来”，也有线索可以继续查。

## 第一次打开，可以按这条路线玩

不妨用三个专题，体验三种不同的历史变化：

1. **苏联解体**：比较 1991 年初和年末，观察一个政治实体解体后的区域变化。
2. **德国重新统一**：聚焦欧洲，比较统一前后的地图，理解“合并”如何体现在版图中。
3. **非洲独立年**：把视角移到非洲，结合专题文字，观察殖民体系变化与国家独立。

看完后，再试着搜索一个你感兴趣的地区，换几个年份，提出一个自己的问题。

喜欢历史的人，可以从事件走进地图；喜欢地理的人，可以从位置追问历史；前端开发者则可以看看，一条时间轴、一张地图和几组对比，怎样组合成一个可探索的页面。

## 从技术角度看：一张历史地图是怎么“动”起来的？

项目的技术组合是 **Vue 3 Composition API + TypeScript + Vite + d3-geo**，配合 Vitest 和 Playwright 验证数据逻辑与浏览器交互。运行时依赖主要是 Vue 和 d3-geo，没有额外引入地图服务、组件库或状态管理库。

整体数据流可以概括为：

**原始 GeoJSON → 数据预处理 → 按日期筛选边界 → 地理投影 → SVG 绘制 → Vue 交互更新。**

这里最有意思的地方，是把几个不同性质的问题分开处理：数据决定有哪些边界，日期决定显示哪个版本，投影决定怎么画，交互决定读者怎么探索。

### 1. 历史地图的核心，是带有效期的数据

普通地图可以只关心“这个地区的轮廓是什么”。历史地图还要问：“这个轮廓在哪一段时间内有效？”

项目中的边界记录除了几何坐标，还带有政治实体编码、开始日期、结束日期、几何版本标识和原始来源序号。选择日期后，核心判断其实很短：

```ts
function activeAt(
  record: { start: string; end: string },
  date: string,
): boolean {
  return record.start <= date && record.end >= date
}
```

这是项目采用的区间判断逻辑，两端都包含在有效期内。日期统一为经过校验的 `YYYY-MM-DD` 格式，才可以这样直接比较字符串。

拖动年份，本质上是改变查询日期，再从全部记录中取出当时有效的那一组。常规年份模式使用年末日期；专题模式则使用专题明确配置的前后快照日期。

**年份只是交互入口，具体日期才是地图查询依据。** 这样，“看 1991 年”和“看苏联解体前后”就能共用数据筛选逻辑，同时保留各自的时间口径。

### 2. 历史名称、事件日期和边界变化，分别建模

名称改变，未必伴随轮廓改变；一份新的数据记录，也未必意味着发生了领土变化。

项目将中文历史名称放在日期相关的显示逻辑中，将事件说明与前后快照放在专题配置中，将轮廓保留在边界数据中。例如同一个来源名称，可以根据日期显示为“俄罗斯帝国”“苏联”或“俄罗斯”；这属于名称层的处理，不能自动推导出几何变化。

一个专题还需要独立配置事件日期、比较日期、关联地区、地图聚焦位置和参考资料。苏联解体专题比较年初与年末，而不是机械地把事件日期前一天、后一天拿来对照。

这种拆分值得借鉴：**同一张页面上看起来相关的信息，不一定应该用同一个字段表达。** 把它们分开，才能准确解释为什么发生了事件，画面却未必马上变化。

### 3. d3-geo 负责算路径，Vue 负责交互

GeoJSON 保存的是经纬度，浏览器绘制需要的是平面坐标。项目使用 d3-geo 的 `geoNaturalEarth1` 投影，再通过 `geoPath` 把地理几何转换成 SVG 路径。

SVG 中的每个地区都可以绑定选择、悬停等交互。拖动与缩放主要更新地图容器的平移和缩放变换；专题聚焦则先把目标经纬度投影到画布，再计算相应偏移。

这是一种职责清晰的搭配：d3-geo 处理地理计算，Vue 通过响应式状态更新页面。这里使用的是 D3 的地理模块，并不需要把整套页面交给 D3 操作 DOM。

SVG 也有适用范围。随着边界细节、可见要素和交互复杂度增加，路径计算与浏览器绘制都可能成为开销。如果继续扩展，应先测量实际瓶颈，再考虑几何简化、按需加载或 Canvas、WebGL 等方案。

### 4. 性能优化从减少重复工作开始

读取地图数据后，项目使用 `shallowRef` 保存边界数组，避免默认对大量嵌套坐标建立深层响应式追踪。日期变化时，通过 `computed` 派生当前可见记录，搜索结果也基于这份记录生成。

地图组件还按要素 ID 缓存 SVG 路径与投影质心。在投影保持不变的前提下，回到已经显示过的边界记录，可以复用计算结果。

这并不意味着每次切换都没有成本：仍然需要筛选记录、更新页面和绘制路径。但它把“哪些数据变化了”和“哪些计算可以复用”区分开了。

一个小项目不一定需要先引入复杂架构。让状态有明确来源，让派生值自动计算，让稳定结果可复用，往往就能解决一批实际问题。

### 5. 数据预处理还要解决“看起来不对”的地图

地理数据能被 JSON 解析，不代表它一定能被正确绘制。

预处理脚本保留原始坐标精度，并根据球面面积判断，在必要时调整多边形环的方向，以适配 D3 的球面几何约定。环方向解释错误时，绘图库可能把一个地区之外的大片区域当成内部。

脚本还记录原始文件哈希、原始几何哈希、来源记录序号和处理说明，并生成核查台账，检查记录有效期的重叠与空档。

这让地图不只有“能展示”的结果，也有“能追溯”的依据。尤其是历史数据，后续修订需要知道某条记录从哪里来、做过哪些转换，而不能只留下一份难以解释的最终文件。

### 6. 静态部署，也有需要验收的细节

地图数据随站点保存，运行时不依赖外部地图瓦片或字体，也无需申请地图 API Key，因此可以作为静态网站部署到 GitHub Pages。

但仓库站点位于 `/history-atlas/` 子路径。构建时需要配置对应的 base，数据请求也通过 `import.meta.env.BASE_URL` 拼接资源路径，避免本地能打开、上线后却加载不到地图。

项目的部署工作流包含安装、lint、单元测试和构建，其中构建脚本先执行 Vue 的类型检查。Playwright 浏览器测试有独立命令；它并未包含在当前 Pages 部署工作流中，不能把“部署成功”理解为所有交互都已经验证。

技术上的轻量，意味着可以少维护一些服务；需要验收的用户体验仍然包括加载失败、重试、手机布局、键盘操作、弹窗焦点和缺数据年份。

## 从这个项目聊聊：AI 制作万物，究竟可以怎么开始？

给地图加一条时间轴，也是一个关于“把好奇心做成作品”的例子。

过去，一个念头可能停留在收藏夹里：想看懂历史版图，想做一个音乐练习工具，想把自己的旅行安排变成可交互路线。现在，AI 可以参与需求梳理、代码实现、界面调整和问题排查，让个人更容易动手做出第一版。

对于“AI 制作万物”，我更愿意把它理解成一种创作机会：**把你在意的问题，做成别人也能打开、操作和理解的东西。**

下面是结合这个项目结构整理的一条可复用路线，不是对具体模型、提示词或实际开发过程的逐步还原。

### 第一步：把“做一个网站”变成一个可观察的体验

“帮我做一个历史地图网站”可以生成很多不同的东西。更明确的需求应该描述使用者能做什么：

> 做一个中文历史地图探索器。用户选择日期后，看到数据源在该日期有效的边界；选择历史专题后，可以切换明确标注日期的前后快照。超出数据覆盖范围时显示缺口，不推测未知国界。

这段描述已经包含了交互、数据规则和失败边界。它让 AI 更容易产出符合目标的实现，也让人有依据判断结果对不对。

同样的方法可以迁移到其他作品：先说明谁来用、完成什么动作、看到什么结果，再讨论技术栈和页面细节。

### 第二步：围绕一条完整路径，做出最小版本

一个历史地图产品很容易不断扩张：增加更多年代、战争过程、人口统计、城市故事、收藏和分享……

第一版可以先围绕一条完整路径展开：**选日期 → 看地图 → 选专题 → 比较快照 → 查资料。**

让 AI 分别协助处理日期逻辑、地图组件、专题配置和布局，比一次要求“生成完整历史平台”更容易检查。每完成一块，就让它接回这条体验路径，确认读者能够走通。

最小版本的价值，在于早点发现真正的问题：数据能否支持想要的比较？用户能否理解快照日期？手机上能否找到专题入口？这些答案会影响后续应该加什么。

### 第三步：把“帮我检查一下”换成具体的验收问题

对于这种项目，可以要求 AI 协助编写和运行以下检查：

- 日期处于有效区间两端时，是否选中了正确记录？
- 选择 2026 年时，是否明确展示数据缺口？
- 切换专题前后，查询日期与界面标注是否一致？
- 改变年份后，是否还保留了已经不存在于当前地图的选择？
- 播放过程中打开弹窗，是否正确暂停并保持内容可读？
- 手机上是否出现横向溢出，键盘能否完成主要操作？

这里既有适合单元测试的数据规则，也有需要浏览器测试的交互问题。

AI 生成代码的速度可能很快，而这些检查让“完成”有了具体定义。一个页面看起来像成品，和它在真实操作中表现可靠，是两个都需要检验的维度。

### 第四步：把事实与许可，纳入产品设计

AI 可以帮助整理历史材料、提出检索线索和生成处理脚本，但历史边界的证据、数据许可和争议口径，仍需要逐项核实。

对于这个项目，640 条记录仍待复核、2020—2026 年缺少数据，都应当直接影响页面行为。它们不是上线前补一段免责声明就能解决的问题：没有可靠数据的年份，就不应绘制未经依据支持的边界。

借助 AI 做其他作品，也可以沿用这个判断：涉及金额，核对计算与币种；涉及音乐资料，核对版权；涉及健康信息，核对来源与适用范围。领域规则需要落到数据、交互和验收里。

### 第五步：留下能继续维护的作品

一次生成的页面，如果没有数据来源、构建方式和验证步骤，下一次修改很容易重新猜测。

这个项目保留了数据处理脚本、来源说明、核查台账和测试。它们让后续维护有机会沿着原有依据继续推进，也能给下一轮 AI 协作提供上下文。

“AI 制作万物”带来的吸引力，是让更多个人想法获得实现的机会。与此同时，创作者的判断仍然很关键：选什么问题，保留什么边界，用什么证据判断作品已经达到预期。

**会提出具体问题，愿意检查结果，能够持续修订——这些能力，会随着实现门槛降低而变得更有价值。**

## 地图很直观，但直观不等于已经考证完成

介绍这个项目，也需要把当前版本的边界讲清楚。

国界数据来自 **ETH Zurich 的 CShapes 2.0**。它采用特定的政治实体编码口径，不是完整的主权国家名录，也不是逐日军事控制线地图。小面积变化、部分日期和历史边界处理，都有数据源自身的限制。

当前保留的 **640 条来源记录均处于未复核状态**。能选择具体日期，表示可以按来源日期检索，并不表示每一天的国界都已经完成独立考证。争议区域的呈现沿用数据源编码，不代表项目作出主权归属判断。

因此，现阶段更适合把它当作 **历史探索与资料查阅的入口**。用于严肃研究、教学引用或具体边界判断时，仍需回到原始资料交叉核实。

地图数据使用 **CC BY-NC-SA 4.0** 许可，限非商业用途；分享改编数据需要署名并沿用同一许可。若计划商用，需要另行取得许可或替换数据源。

## 下一次遇到一个历史年份，试着把它放回地图

地图上的线条看起来很安静，背后却可能是漫长的谈判、战争、独立与重组。

「经纬之间」想做的，就是给这些线条加上时间，让读者多一个理解历史的入口。

从技术上看，它是数据、日期、投影和交互的组合；从创作上看，它也提醒我：一个个人作品可以从一个很具体的好奇心开始。借助 AI，可以更快尝试实现；而让作品值得分享，仍需要清晰的设计、可追溯的资料和实际验证。

下一次读到“1991 年苏联解体”或者“1990 年德国统一”，除了记住年份，也可以打开地图，看看变化发生在哪里，再追问它为什么发生。
