## 这题看起来很基础，实际上很容易露馅

如果我是面试官，我大概率不会直接问：

“`dependencies` 和 `devDependencies` 有什么区别？”

原因也很简单，这题太像背诵题了。很多人张口就来：

- `dependencies` 是生产依赖
- `devDependencies` 是开发依赖

听起来没毛病，但也基本等于没说。

真正一上项目，问题马上就不是“你背没背过定义”，而是：

- 这个包到底是谁在用
- 它出现在开发阶段、构建阶段，还是运行阶段
- 线上机器如果只装生产依赖，会不会直接翻车

这几个问题一旦想明白，`package.json` 里的依赖分类其实没那么玄学。想不明白，就很容易把 `axios` 塞进 `devDependencies`，然后在生产环境里喜提一个 `Cannot find module`。

## 真正的判断标准，不是“开发时用不用”

很多人第一次分依赖时，脑子里的标准是：

“我开发时用到了它，所以它应该算开发依赖吧？”

这就是最常见的坑。

更靠谱的判断方式其实就一句话：

**看这个包是不是生产运行时必需的，而不是看你开发时有没有碰过它。**

换句话说，可以这样理解：

- `dependencies`：项目跑起来时真的要用到
- `devDependencies`：只在开发、构建、校验、测试阶段使用

注意，很多包虽然你每天都在用，但最终线上真正运行的时候，已经完全见不到它了。这类包通常都应该进 `devDependencies`。

## 用 Vue3 + Vite 项目举个最典型的例子

假设一个项目里装了这些包：

- `vue`
- `axios`
- `vite`
- `typescript`
- `eslint`
- `sass`

比较合理的划分一般是这样：

```json
{
  "dependencies": {
    "vue": "^3.x",
    "axios": "^1.x"
  },
  "devDependencies": {
    "vite": "^x.x",
    "typescript": "^x.x",
    "eslint": "^x.x",
    "sass": "^x.x"
  }
}
```

### 为什么 `vue` 要放 `dependencies`

因为浏览器里真正执行应用代码时，需要 `Vue` 提供运行时能力。

比如这类代码：

```ts
createApp(App).mount("#app");
```

没有 `vue`，应用根本起不来。所以它不是“开发时才用”，而是“上线后也必须存在”。

### 为什么 `axios` 也要放 `dependencies`

因为只要你的业务代码里真的发请求：

```ts
import axios from "axios";
```

那运行时就需要它。无论你本地开发、测试环境，还是正式生产环境，项目只要执行到这行代码，就离不开 `axios`。

把它放到 `devDependencies` 最大的问题不是“语义不优雅”，而是某些部署方式下真的会出事故。

### 为什么 `vite` 放 `devDependencies`

很多人容易在这里绕进去。

`Vite` 明明参与了整个项目开发和构建，为什么不算生产依赖？

因为它参与的是**构建过程**，不是**应用运行过程**。

你可以把流程想成这样：

```text
源码
  -> Vite 处理、打包
  -> 生成 dist
  -> 浏览器加载 dist 里的 js / css / html
```

发布之后，真正在线上跑的是 `dist` 里的静态资源，不是 `Vite` 本人。它干完活就下班了，并不会跟着用户的浏览器一起继续上班。

### `TypeScript`、`ESLint`、`Sass` 为什么也通常是 `devDependencies`

- `TypeScript` 负责类型检查和编译辅助，最终浏览器不会直接运行 `.ts`
- `ESLint` 负责代码规范检查，属于开发质量工具
- `Sass` 负责把 `.scss` 编译成 CSS，最终用户拿到的是编译结果，不是 Sass 编译器

它们都很重要，但重要不等于要陪着生产环境一起装机。

## 一个很常见的反向翻车案例

再看一道更有区分度的题：

如果有人把 `axios` 放进了 `devDependencies`，把 `vite` 放进了 `dependencies`，会怎么样？

先说结论：

- `axios` 放错，比 `vite` 放错更危险
- `vite` 放错，不一定立刻坏，但通常是浪费

### `axios` 放到 `devDependencies` 的风险

如果线上环境执行的是：

```bash
npm install --production
```

那么 `devDependencies` 不会被安装。

这时候如果你的服务端运行、SSR 过程、脚本执行，或者某些构建后仍然依赖 Node 环境的逻辑需要 `axios`，就可能直接报错。

哪怕是纯前端项目，这种分类方式也容易误导团队。今天只是没炸，明天切换部署方式、补一个服务端渲染、或者加一个构建后脚本，问题就来了。

### `vite` 放到 `dependencies` 的影响

通常不会直接导致功能错误，因为用户最终访问的是构建产物，不是 `Vite`。

但坏处也很现实：

- 生产环境安装体积变大
- 安装耗时更长
- 依赖树更重
- 团队成员更容易对“谁是运行时依赖”产生误解

说白了，它不太像“致命 bug”，更像“仓库里多囤了几箱根本不会上桌的食材”。

## 为什么这道题本质上考的是工程化链路

我觉得这类题最有意思的地方，不是考你会不会背命令，而是看你有没有把前端项目的生命周期串起来：

```text
源码 -> 开发 -> 构建 -> 部署 -> 浏览器运行
```

很多人卡住，就是因为把这几件事混成了一锅粥。

尤其是下面这个问题，很适合拉开差距：

**为什么 `Vite` 明明参与生成最终页面，却一般放 `devDependencies`，而 `Vue` 要放 `dependencies`？**

答案就在于：

- `Vite` 服务于构建阶段
- `Vue` 服务于运行阶段

一个是“做饭的厨具”，一个是“端上桌的菜”。你当然不能把锅端给客人吃，但你也不能做完菜发现盘子里啥都没有。

## 顺手把几个常见 npm 命令也捋一遍

聊依赖分类时，面试里经常还会顺手追问这几个命令。

### `npm install`

默认会安装项目依赖，通常包含 `dependencies` 和 `devDependencies`。

适合本地开发环境，大家日常敲得最多的也是它。

### `npm install --production`

只安装生产依赖，也就是 `dependencies`。

它常见于线上部署、精简安装，或者某些只关心运行时依赖的环境。

所以只要一个包在生产运行阶段真的会被用到，就别把它手滑塞进 `devDependencies`。

### `npm ci`

这个命令特别适合 CI/CD。

它会严格按照锁文件安装，强调的是**一致性**。对持续集成环境来说，这比“能装上就行”重要得多。

团队里如果大家本地各装各的，线上和测试环境又靠运气复现，那 bug 排查基本就是玄学修仙。

## 拿我这个博客项目举个真实例子

上面一直在聊 Vue3 + Vite，但我最近整理这个博客项目时，也一样会按这个标准来分。

这个项目本身是 `Next.js 16 + React 19 + TypeScript`，当前的依赖划分大致是这样的：

```json
{
  "dependencies": {
    "next": "16.2.10",
    "react": "19.2.4",
    "react-dom": "19.2.4",
    "gray-matter": "^4.0.3",
    "next-mdx-remote": "^6.0.0",
    "giscus": "^1.6.0",
    "zod": "^4.0.5"
  },
  "devDependencies": {
    "typescript": "^5",
    "eslint": "^9",
    "vitest": "^4.1.10",
    "@types/node": "^22.20.1",
    "@types/react": "^19"
  }
}
```

为什么这么分？

- `next`、`react`、`react-dom` 是运行这个站点本身需要的
- `gray-matter`、`next-mdx-remote`、`zod` 属于内容解析和运行流程的一部分
- `giscus` 是页面评论功能依赖的运行时代码
- `typescript`、`eslint`、`vitest` 则主要负责开发、检查和测试

虽然技术栈换了，但判断标准完全没变。

这也是我现在看依赖最习惯的方式：**别问“开发时用不用”，要问“上线后还需不需要它继续干活”。**

## 面试里如果要一句话说清楚，我会怎么答

如果现场时间很紧，我会把答案压缩成下面这版：

> 区分 `dependencies` 和 `devDependencies`，关键不是开发阶段有没有用到，而是生产运行时还需不需要这个包。像 `Vue`、`axios` 这种运行时要参与执行的库放 `dependencies`；像 `Vite`、`TypeScript`、`ESLint`、`Sass` 这种只参与开发、构建、检查的工具放 `devDependencies`。线上如果只安装生产依赖，通常不会装后者；如果部署的是已经构建好的产物，一般不影响运行。

这版不花哨，但至少说明你理解的是项目链路，不是名词释义。

## 最后给自己留一个判断口诀

以后再看到一个新包，不知道该往哪边放，可以先别急着拍脑袋，问自己两个问题：

1. 这个包在生产运行时会不会真的被执行到？
2. 它是业务的一部分，还是构建、检查、测试过程里的工具？

如果还是纠结，那就把它丢到整个流程里看一遍：

```text
它是在写代码时帮忙，
还是在打包时干活，
还是在应用真正跑起来后继续参与执行？
```

很多工程化问题，最后都不是 npm 的问题，而是你有没有把“谁在什么时候干什么”想清楚。

一旦这个视角有了，`dependencies` 和 `devDependencies` 这题就不再是八股，而是常识。
