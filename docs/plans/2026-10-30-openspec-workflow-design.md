# 栈间笔记 OpenSpec 工作流设计

## 背景

项目已经使用 `docs/plans` 保存设计和实施计划，但不同规模的需求没有统一的规格入口。随着站点功能、内容迁移、发布规则和隐私约束持续增加，需要在写代码前固定需求边界、可验证行为和风险。

## 目标

- 为跨文件、跨模块或有隐私/发布风险的变更提供统一的规格记录。
- 保留现有 `docs/plans` 的长期文档，不引入生产依赖或外部服务。
- 让规格可以被脚本自动检查，尽早发现缺少章节、未完成任务和不安全内容。
- 允许小型、明确的内容修订和样式修正跳过完整流程。

## 方案选择

### 方案 A：引入第三方 OpenSpec CLI

使用外部 CLI 管理目录、命令和生命周期。优点是约定完整；缺点是增加工具版本、安装和团队学习成本，与当前仓库的轻量维护方式不匹配。

### 方案 B：轻量 Git 原生 OpenSpec（采用）

使用 Markdown 规格和一个无依赖 TypeScript 校验脚本。每个变更放在 `openspec/changes/<change-id>/`，生效规格放在 `openspec/specs/`；`docs/plans` 继续保存已经确认的长期设计和实施计划。优点是透明、可审查、无需改变构建链，适合当前单仓库博客。

### 方案 C：只扩展 `docs/plans`

为现有计划增加 proposal/spec 章节，不创建独立目录。改动最少，但无法区分“正在提议的变更”和“当前生效的规格”，也不利于归档与自动检查。

## 目录与生命周期

```text
openspec/
├── README.md
├── specs/                         # 当前生效的领域规格
└── changes/
    └── <change-id>/
        ├── proposal.md            # 背景、目标、范围、风险
        ├── spec.md                # 可验证的 SHALL/MUST 行为
        ├── design.md              # 技术方案、取舍、数据流
        └── tasks.md               # 实施、测试、文档和验收任务
```

生命周期为：提出变更 → 评审 proposal/spec/design → 拆解 tasks → 实现并验证 → 将最终规格合并到 `specs/` → 在变更目录记录完成状态或归档。没有必要的变更可以直接修改现有文档，但涉及公开内容、迁移、数据结构、路由、外部服务或安全边界时应先建立变更目录。

## 校验规则

`npm run openspec:check` 检查：

- 变更 ID 只包含小写字母、数字和连字符。
- 每个变更包含 `proposal.md`、`spec.md`、`design.md`、`tasks.md`。
- 四份文件包含规定的一级标题。
- `tasks.md` 至少包含一个任务，并拒绝仍有未勾选任务的已完成标记。
- 文档不包含常见凭据字段或私钥标记。

校验器只读取文件，不修改内容，不连接网络。命令可以指定目录，便于测试和未来迁移。

## 验收

- 新目录和模板能够说明何时使用 OpenSpec。
- 校验器对有效、缺文件、错误命名、未完成任务和疑似凭据分别给出明确结果。
- README、AGENTS.md 和 package scripts 都能找到使用入口。
- `npm test`、`npm run lint`、`npx tsc --noEmit` 和 `npm run build` 通过。
